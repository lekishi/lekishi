= RFD 3 chapter content boundary decision

== Provenance and scope

RFD 4's Wave 2 work connects the reviewed Tang chapter
(`historical/chapters/tang-mission-750-754/`, merged in PR #10) to the browser
atlas. Until this change the atlas rendered `src/lib/atlas/fixtures.ts`, a
synthetic foundation fixture, so the deployed Pages preview showed placeholder
events while the reviewed chapter existed only in the repository.

This record is that decision, taken on 2026-09-24 from the measurement in
<<Measured evidence>>. It does not supersede
link:STATIC_ARCHITECTURE.adoc[the static architecture decision]: the site stays a
prerendered static artifact with no server, and RFD 2 stays the owner of
historical meaning. It records how reviewed content crosses from the versioned
contract into the browser, which is the part the two earlier records left open.

== Decision

The atlas renders the reviewed chapter through one browser-safe boundary, and
that boundary is the only path chapter content takes into the app.

* `src/lib/historical/chapter.ts` stays the Node-side loader. It reads the
  content tree with `fs` and hands it to the contract's own
  `Publication.checkAll`. Tests and tooling use it; the browser never imports it.
* `scripts/check-chapter.mjs` runs before Vite in `pnpm build` and runs the
  chapter's contract test and the projection test suite through Vitest, so an
  edited approved revision, a missing source pin, or a record published at a
  revision it does not carry fails the build. This is the validation gate: the
  validator needs `node:fs` and `node:crypto`, so it cannot run in the bundle,
  and running it through the existing test suite keeps it the single source of
  truth instead of a second implementation.
* `src/lib/atlas/chapter-content.ts` bundles the same records and publication
  sets with Vite's `import.meta.glob`. The browser therefore reads the files the
  contract validates: no `fs`, no second copy of the content, no fetch, and no
  request a static host has to serve.
* `src/lib/atlas/projection.ts` selects the newest published revision per record
  through the contract's own publication ordering and maps the published
  revisions into the renderer-independent atlas domain. `currentPublished` moved
  into `src/lib/historical/contract/publication-order.ts` — browser-safe, no Node
  API — and `publication.ts` re-exports it, so the browser projection and the
  Node-side validator cannot disagree about what is published.
* The projection runs at module scope in the atlas's module graph and throws when
  the chapter cannot be projected. The atlas route is prerendered, so an invalid
  chapter fails `pnpm build` (and therefore the Cloudflare Pages build) instead of
  shipping placeholder content, and a deployed page never falls back to synthetic
  events.
* `src/lib/atlas/fixtures.ts` stays, as synthetic content that only focused unit
  tests import. `scripts/check-static-build.mjs` fails the build if any of its
  strings reach the artifact.

=== What the projection refuses to do

These are contract-with-the-reader rules, not implementation details:

* The newest published revision wins. A retained earlier revision — v1 beside the
  v2 corrections — can never reach the atlas, and a mirror that disagrees with the
  newest set fails the projection.
* An event keeps its whole support interval. An event with no published map
  position (no place named, no sourced identification, or a place named only as
  context) stays in the non-map list with no coordinate.
* A place whose published geometry is `unknown` carries no position. A
  `display_anchor` stays a display anchor, and a display anchor that carries a
  stated precision fails the projection: the atlas must not show a coordinate the
  review never approved.
* The occurrence mode survives to the surfaces, not only to the data. A duration
  is active at the playhead, an uncertain occurrence window is only ever a
  possible match — it is one occurrence at an unknown point inside the span, so
  the atlas never animates it as continuous activity — and the list and the
  details surface say which one it is rather than showing identical wording.
* The coda distinction is the chapter's own presentation label, cross-checked
  against the primary mission window. A coda node moved into the window, or a
  mission event moved out of it, fails the projection rather than being folded in.
* Route geometry fails rather than being flattened into points; so do an undated
  event and an open-ended occurrence, which the atlas window cannot represent
  without inventing the missing end. These are recorded gaps, not silent
  omissions (see <<Limitations recorded>>).

=== Alternatives considered

* **A second hand-written fixture.** Rejected: it duplicates 65 records of
  reviewed truth and would drift from the content the contract validates.
* **A generated module written by a build script.** Rejected: the projection
  needs the contract's TypeScript in Node, which means either a second build step
  or a generated file to keep in sync; the runtime path is simpler and is the same
  code the tests exercise.
* **Fetching a projected JSON file at runtime.** Rejected: it adds an async load
  and a request for content the bundle already carries, and the atlas would show
  nothing until the fetch resolved.
* **A Vite plugin that projects at build time into a virtual module.** Measured
  and rejected: a plugin can import the Node-side loader and fail the build, and
  it works, but Vite then warns that the config's inlined module graph uses
  extensionless imports the future native config loader will not resolve. The
  prerender already fails the build on a module-scope throw, so the plugin buys
  nothing for that warning and a config-file dependency on the content tree.

== Consequences

* The deployed artifact renders the reviewed chapter's events, not placeholder
  events. Page metadata, the workspace notice, the event list, and the selection
  panel name the chapter and state its recorded review status.
* The atlas states what it cannot show instead of filling it in: unplaced events
  are listable and unmarked, and the details surface says why.
* The event list is the panel's scroll container, and the overlay column is
  bounded above the time controls at every width, so a window longer than the
  panel scrolls instead of running under the controls.
* Adding or changing a chapter is now a content decision with a code path that
  fails loudly, rather than a fixture edit.
* No server, database, provider account, or secret is introduced; the artifact
  still contains only prerendered HTML, hashed JS/CSS, and the Cesium runtime.

== Limitations recorded

* **Not AC2 and not AC3.** The owner's editorial approval of the published
  revision is still pending, the specialist reviews the feasibility report
  identifies have not been performed, and the atlas has no search, sources,
  story-navigation, or layer controls. This change connects reviewed content to
  the existing workspace; it does not complete the exploration loop.
* **Coda nodes need a window change.** The atlas opens on the primary 750–754
  window. The five coda nodes are outside it and appear, labelled, only when the
  window is widened; there is no story navigation to reach them yet.
* **Undated and open-ended occurrences are rejected.** The atlas window is closed
  at both ends, so the projection fails on a wholly undated event or an
  `lower_only`/`upper_only` interval rather than guessing. RFD 4 AC3's
  "undated events stay discoverable" behavior is not implemented.
* **Areas and routes are rejected.** The atlas domain draws points; a
  `source_supported_area`, an itinerary, or a reconstructed route fails the
  projection. The chapter asserts no route, so this is a future-content gap.
* **Map labels crowd at the whole-globe view.** The renderer labels every event
  with its reviewed caption, and the chapter's events cluster on the Inland Sea
  and the Chinese coast, so labels overlap until the camera moves in. Cesium's
  entity API in this version exposes no label collision detection, so decluttering
  is a renderer decision rather than a content one.
* **Superseded revisions ship in the bundle.** The retained v1 revisions are part
  of the reviewed tree, so the client chunk carries them; the rendered view is the
  published revision only, and the retained history is what a future correction
  view needs.
* **Tablet evidence is Chromium touch emulation, not a physical iPad.** Physical
  device acceptance remains a separate gate under RFD 4.

  with its invariant, and the Playwright suites against the built artifact.
* Inspected the artifact directly: the prerendered atlas shell names the reviewed
  chapter, the chapter chunk carries the published chapter and a published event
  id, and no synthetic fixture string appears in the built scripts.
