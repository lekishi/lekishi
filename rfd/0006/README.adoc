= RFD 6 Signed-in drafts on the published site

== Why now

The owner asked on 2026-10-21 for sign-in on the site, so that members of the
`lekishi` GitHub organization can see draft and unapproved chapters on the
published site while everyone else sees only approved ones. GitHub is the first
identity provider; other providers and OIDC come later. Pull-request previews
keep showing every draft without sign-in. The owner added the same day that a
missing approval must never fail a build.

Today the published site cannot do this. It is a static artifact
(link:../0003/STATIC_ARCHITECTURE.adoc[RFD 3's static architecture decision])
and a production build leaves drafts out at build time, so there is nothing
behind which to put a sign-in. This RFD proposes what a production build ships
for members, what gates it, and how that sits with the publication gate of
link:../0002/AUTHORING_FORMAT.adoc[RFD 2's authoring format].

== Where things stand

* *Publication.* A chapter is published when its manifest carries the owner's
  digest approval of its exact content. `pnpm approvals` lists and diffs the
  chapters; only the owner approves. `.github/CODEOWNERS` requires the owner's
  review on every manifest.
* *Production* (`main`, `lekishi.pages.dev`) serves approved chapters only. Until
  now a stale approval failed the production build. Per the owner's message of
  2026-10-21, PR #26 is changing that: a production build drops a draft or stale
  chapter with a warning, and CI's `publication` job reports pending approvals
  without going red. This RFD builds on that rule: _an unapproved chapter is never
  in the public site, and never a build failure_.
* *Previews* (the dev server and every non-`main` Cloudflare Pages build,
  `draftChaptersServed()` in `scripts/dev-pages.mjs`) serve every chapter, drafts
  under a Draft banner and pill, by the owner's decision of 2026-10-18.
* *Exposure today.* The repository is private, but preview URLs
  (`<branch>.lekishi.pages.dev`) are public: anyone holding one sees the drafts
  of that branch. Signing in on production therefore protects the published
  site's reading of the history, not the secrecy of the drafts. This RFD keeps
  previews open, as asked; gating them is a separate, later choice (see
  <<Open questions>>).

== What stays public

Unchanged for a reader who is not signed in:

* the home page, its cards and `/search-index.json`, listing approved chapters only;
* every approved chapter at `/chapters/<id>` and its deep links;
* the globe tiles, fonts, brand assets, attribution and `404.html`.

New and public: a quiet "Sign in" control (placement is RFD 5's call) and the
`/auth/*` endpoints behind it. Nothing else.

Not public, and checked by the build invariant: a draft's id, title, summary or
any of its data, in any static file or client chunk. Today the `virtual:lekishi-chapters` index lists every manifest,
drafts included, so a production build already ships draft titles in public
JavaScript; the first step of the implementation closes that.

== Proposal

The proposal has two halves. The first is where drafts live in a production
build and how a member reaches them. The second is what checks the member, where
the alternatives differ. The recommendation follows
https://github.com/renga-dcim/rfd[renga-dcim/rfd], whose site already shows
private RFDs to signed-in members of its GitHub organization on Cloudflare
Pages.

=== Prior art: renga-dcim/rfd

Read on 2026-10-21 at its `main`:

* The SvelteKit app runs on `@sveltejs/adapter-cloudflare`, so pages render in a
  Pages worker.
* `src/lib/server/github.js`: an OAuth App asks for `read:org`, the callback
  exchanges the code, checks `GET /user/memberships/orgs/<org>` is `active`, and
  drops the token.
* `src/lib/server/session.js`: a stateless session cookie, the login and an
  expiry signed with HMAC-SHA-256 under `SESSION_SECRET`; a week long.
* `src/hooks.server.js` reads the session into `locals.user` and sets
  `Cache-Control: private, no-store` for signed-in readers, `Vary: Cookie`, and
  `X-Robots-Tag: noindex`.
* The RFDs are bundled into the server only. A private RFD is a 404 to anyone
  signed out and is missing from every list and count.
* Without the three secrets, `/auth/login` answers 503 and everyone sees the
  public RFDs; previews work signed out.

Lekishi differs in one way that matters: almost all of it (the globe tiles, the
fonts, every approved chapter) must stay prerendered static files. SvelteKit
allows that on the same adapter.

=== Drafts render in the worker, approved chapters stay static

With `adapter-cloudflare`, a route that is prerendered is written out as a
static file and listed in the generated `_routes.json` as excluded from the
worker, so the reader site keeps being served as plain files, with no worker
invocation. Only what is not prerendered reaches the worker. A production build
then splits:

* *Static, as today:* the home page, `/search-index.json`, every approved chapter
  at `/chapters/<id>`, the tiles, fonts and brand assets.
* *Worker, members only:* a draft or stale chapter at its own `/chapters/<id>`,
  `/drafts.json` (the drafts' cards) and `/drafts/search-index.json`, and
  `/auth/login`, `/auth/callback` and `/auth/logout`.

The chapter route uses `prerender = "auto"`: its `entries` are the approved
chapters, prerendered as now; any other id falls through to the worker, whose
load returns the draft when `locals.user` is a member and a 404 otherwise, the
same 404 as an id that does not exist. A member's link to a draft is therefore
the address it keeps once approved.

Draft data is compiled with the preview set (`compileAll` with `preview: true`),
the same content a pull-request preview shows, and is bundled into the server
only, as renga's RFDs are. It never becomes a static file or a client chunk,
which is what keeps it from strangers: every file in `_app/immutable/` is public
and listed from public JavaScript. To make that hold, the chapter's data moves
from the universal load's dynamic import of `virtual:lekishi-chapters/<id>` to a
server load (`+page.server.ts`); a prerendered chapter's data is then written as
its `__data.json`, a draft's is answered by the worker. The public
`virtual:lekishi-chapters` index carries served chapters only.

A signed-in member also sees drafts on the home page and in search. Both stay
prerendered; after mount, when the readable hint cookie is present (see
<<Sessions>>), the page fetches `/drafts.json` and adds the drafts' cards with the
Draft pill, and the search dialog merges `/drafts/search-index.json`. Anonymous
readers make no extra request.

The drafts say they are drafts. `release.ts`'s `DRAFT_SCOPE` reads "This build is
a preview" today; for a member on production the line becomes "Visible to
signed-in lekishi members; not published." Every other draft statement stays.

Previews are unchanged: a preview build prerenders every chapter, drafts
included, under the banner, and needs no sign-in. The worker is deployed there
too but holds no secrets, so `/auth/login` answers 503 and no route depends on a
session.

=== The gate

==== A. Sign in with GitHub in the SvelteKit app (recommended)

The auth is renga's, adapted:

* `src/lib/server/github.js` and `src/lib/server/session.js` nearly as renga has
  them; `src/hooks.server.ts` sets `locals.user`; `/auth/login`, `/auth/callback`
  and `/auth/logout` (a POST) as routes. The provider sits behind the two
  functions `authorizeURL` and `member`, so OIDC later is a second module plus an
  allow-list or group claim.
* The identity is renga's OAuth App with `read:org`, owned by the `lekishi`
  organization. A GitHub App with the Members permission read-only would scope
  tighter than `read:org`, which reads every organization the reader belongs to;
  renga's choice is the proven path, and the GitHub App can follow.
* Secrets, set for Production only: `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`,
  `SESSION_SECRET`.

Pros:

* It is what the owner asked for: a sign-in inside the app, on the same site and
  the same addresses.
* It is proven: renga's site runs the same code on the same host.
* Everything is in the repository, reviewed and tested in Vitest.
* Draft data never exists as a file, so no routing rule can leak it.
* Works on `lekishi.pages.dev` as it is, with no custom domain or Zero Trust
  account.

Cons:

* It changes the adapter, from `adapter-static` to `adapter-cloudflare`, and adds
  the site's first runtime code and secrets. That reverses `AGENTS.md`'s "no
  runtime server" and "no secret, token or account" rules for the drafts and
  sign-in, and supersedes part of RFD 3's static architecture decision; the
  reader site stays static. The deploy output moves from `build/` to
  `.svelte-kit/cloudflare`, and the build invariant, `pnpm preview` and the e2e
  static mode follow it.
* Chapter data reaches the browser as `__data.json` rather than a JS chunk; the
  payload is to be measured against RFD 4.
* We own security-sensitive code, if small: state, cookie signing, expiry.
* A removed member keeps access until their session expires.
* Worker requests count against the Workers free quota (100,000 a day), which
  members-only traffic will not approach since static files never invoke it.

==== B. Cloudflare Access in front of the drafts

A Cloudflare Zero Trust application covers the drafts' paths on
`lekishi.pages.dev` with GitHub as the identity provider and a "member of GitHub
organization `lekishi`" rule. The worker trusts Access's signed assertion
instead of a session of ours.

Pros:

* No sign-in code and no session cryptography of ours.
* Other providers and OIDC later are a dashboard change, with groups, audit logs
  and immediate revocation. The free plan covers 50 users.

Cons:

* Still needs the worker for drafts at their own address, so it saves only the
  auth modules, not the adapter change.
* A Zero Trust account whose configuration lives outside the repository unless
  kept in Terraform.
* Access on a `*.pages.dev` production hostname, scoped to paths, has documented
  quirks and needs a trial; drafts at `/chapters/<id>` cannot be covered by a
  path rule without covering approved chapters too, so drafts would move under a
  `/drafts/` prefix.
* The sign-in is Access's interstitial rather than the app's.

==== C. A separate drafts deployment

Keep production exactly as it is, and deploy `main` a second time with drafts
on, as a `drafts` branch alias (`drafts.lekishi.pages.dev`) that CI moves to
`main` on every merge, optionally behind Access.

Pros:

* No change to the production artifact, its adapter or its rules.

Cons:

* It is not sign-in on the published site; members use another address.
* Without Access it is another public preview, so it does not meet the ask; with
  Access it carries B's costs.

Rejected outright: keeping `adapter-static` and gating a `/drafts/` tree of static
files with a hand-written Pages Function (the first draft of this RFD), since a
routing mistake would serve the files to anyone and it duplicates what SvelteKit
gives on its own adapter; encrypting draft data with a shared passphrase (no
identity, no revocation); and storing drafts in KV or R2 (more infrastructure
for the same gate).

=== Sessions

As renga: a cookie holding the GitHub login and an expiry, signed with
HMAC-SHA-256, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`; membership is checked
at sign-in only. Renga keeps sessions a week; this RFD proposes 12 hours, so a
removed member loses access the same day. A second, readable cookie,
`lekishi_member=1`, holds no credential; it only tells the prerendered pages to
ask for the drafts, so anonymous readers make no extra request. It is the site's
second piece of browser state after the last position in `localStorage`, which
`AGENTS.md` says needs the owner's decision; this RFD asks for it.

=== The publication gate

Nothing about approval changes. The owner still approves a digest with
`pnpm approvals`, CODEOWNERS still requires the owner on manifests, and no one
else writes an approval. What changes is where an unapproved chapter goes:

[cols="1,1,1",options="header"]
|===
|Chapter state |Public site |Members (production)
|approved |prerendered, served |the same page
|draft (no approval) |404 |rendered by the worker at `/chapters/<id>`
|stale (approval no longer matches) |404, with a build warning |rendered by the worker, stating what changed since the approval
|===

A consequence to accept: editing a published chapter on `main` takes it off the
public site until it is approved again, so a reader's link to it 404s in the
meantime. Today that edit fails the build and the previous deployment stays up;
under PR #26 and this RFD it deploys without the chapter. See <<Open questions>>.

The build invariant (`scripts/check-static-build.mjs`) gains checks:

* no static file or client chunk contains a draft's id, title or summary; only
  the server bundle does;
* every prerendered chapter is approved, and `_routes.json` excludes it from the
  worker;
* a preview build prerenders every chapter.

=== The 20,000-file limit

Drafts add no static files on production: they render in the worker, and the
worker bundle is not a static asset. Approved chapters gain one `__data.json`
each. The artifact stays about 1,500 files
(link:../0003/GLOBE_RENDERER.adoc[the globe renderer record]), and the invariant's
limit stays where it is. `_routes.json` allows 100 rules; the adapter collapses
the static paths into prefixes such as `/globe/*`, which is to be checked on the
first build.

== Alternatives and trade-offs

A against B is the main choice, and with drafts rendered in the worker it is
narrower than it first looked: both need the adapter change, and B saves only
the two auth modules, which renga has already written and run. A keeps
everything in the repository and the drafts at their real addresses. C avoids
every change to production but is not what was asked.

Since previews already expose drafts to anyone with a link, the stakes of a bug
in A are a draft seen early on the published host.

A per-chapter flag instead of the approval state was not considered: members see
exactly what the publication gate has not published, so there is one source of
truth.

== Open questions

* Should a stale chapter's public URL show a "being revised" page instead of a
  404 until it is re-approved? Serving the last approved content would mean
  building it from the approved revision in Git, which is possible but larger.
* Should previews later allow sign-in or sit behind it? The owner wants them
  open now; sign-in on `*.pages.dev` previews would need a second OAuth App, as
  renga notes.
* Session length: 12 hours proposed, a week in renga.
* OAuth App now and a GitHub App later, or the GitHub App from the start.
* Where the "Sign in" control lives, for RFD 5.
