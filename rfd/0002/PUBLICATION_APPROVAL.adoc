= RFD 2 publication approval gate

== Provenance and scope

This record answers a review question from the owner on 2026-09-24, after the
Tang chapter's two publication sets were already in the tree: *"we should have
some sort of decision making checkpoint in terms of publishing so you don't just
go invent multiple versions of data."*

The gap is real. The contract gives every content change one shape — a new
revision named by a publication set — and the atlas reads the newest set-named
revision. Nothing in the schema requires that a *person* decided a new version
of the content may exist: `published_by` accepts any person, and
`review.independence` has no value for the owner's editorial approval (its enum
is `self_review`, `independent_review`, `specialist_review`). The two sets in
the chapter tree were therefore created by the preparing editor alone, and
nothing but prose in their notes records that they are preparation snapshots
rather than approved releases.

This record adds the missing decision point. It does not change the contract
schemas or their version; it changes who may create a set, and it makes the
decision machine-checkable. link:CONTRACTS.adoc[The v0 contract decision] stays
readable and unchanged.

== Decision

Publication is a decision, not an agent action.

* **A publication set may exist only when the ledger below names it.** A set
  that the ledger does not cover fails the build.
* **The preparing editor may write draft revisions but must not create, extend,
  or supersede a set.** Draft revisions leave the previously published revision
  current, so content can be prepared and reviewed without the atlas changing.
* **The ledger records the decision, not the review.** A row says who decided
  that this version of the content may exist and when; the set's own `review`
  block still records the review independence of the content.
* **Three decisions are recorded.** `preparation snapshot` means the owner did
  not decide this content — it exists because preparation was instructed — and
  such a set must carry the preparing editor's `self_review`. `owner decided`
  means the owner decided that this specific content may be published while AC2
  and the specialist reviews stay open. `owner approved` means the owner's
  editorial approval under RFD 2, which is what RFD 4's AC2 asks for. The Tang
  set's row now carries the owner's approval, taken on 2026-09-25; the ledger
  update below records it.
* **Nothing is an official publication until an `owner approved` row exists.**
  The Tang set has one as of 2026-09-25, so it is now the chapter's official
  publication while AC2's remaining parts and the specialist reviews stay open.
  No set may claim the owner's approval without that row.
* **A row binds the decision to the snapshot it was taken on.** Each row carries
  the canonical digest of the set document — members, revision hashes, source
  pins, review, and timestamps — and the gate fails when the set no longer
  matches its row. Changing the content behind a set id therefore invalidates the
  decision instead of silently inheriting it. The digest is a consistency check,
  not an authentication: a person still has to check that the row, the digest,
  and the set actually describe what the owner decided.

The gate is enforced by
`src/lib/historical/contract/publication-approval.test.ts`, which runs in
`pnpm build` through `scripts/check-chapter.mjs`. It reads this record and every
chapter's sets under `historical/chapters/` — so a new chapter directory cannot
appear with an uncovered set — and fails on any of: a set with no ledger row, a
ledger row for a set that does not exist, a decision the gate does not know, a
duplicated row, a `preparation snapshot` that claims independent or specialist
review, a set whose review independence has no owner decision behind it, an
owner decision whose row does not name the owner as the decider, or a set whose
digest no longer matches its row. So an agent cannot mint a version of
the content that no decision covers, and cannot label a preparation snapshot as
reviewed. The gate checks the shape of the record; whether a decision is truly
the owner's is the owner's row to write, which is why the ledger names the
decider in every row.

=== Ledger update — 2026-09-25: the owner approves the Tang set

The owner's instruction of 2026-09-25 was *"Approve 1. Proceed with 2"*, replying
to the request to approve the current merged Tang v1 preparation set for release
or request changes. It is recorded here as the owner's editorial approval under
RFD 2 of the exact set merged on `origin/main` (PR #11, merge commit
`6493852e1e29b2028578f715797be941ea74a017`):

* the decision is the owner's editorial approval under RFD 2, which is what
  RFD 4's AC2 asks for. It is not preparing-editor self-review and not
  independent or specialist review;
* the set document is deliberately unchanged, so the digest in the row still
  matches the snapshot the owner approved. Its `review` block therefore keeps
  `self_review` and its preparation-time notes; changing the set would change
  the digest and invalidate the approval it now carries, which is the
  correction path's own rule;
* the optional specialist reviews the feasibility report identifies (maritime or
  ancient history, Buddhist studies, Tang court history, a philologist) remain
  visibly unperformed. The approval does not imply them;
* AC2's approval-dependent part — the recorded owner's editorial approval of the
  published revision — is satisfied for this set. AC2's visible
  uncertainty/dispute part still depends on the exploration loop, and the AC7
  attribution/rights audit remains open, so AC2 as a whole is not complete and
  is not marked complete.

== Consequences

* Adding a chapter or changing one now has three distinct steps instead of one:
  prepare draft revisions (editorial work), record the decision (owner), and
  publish the set that names them (the mechanical step the atlas reads).
* The atlas keeps rendering the last published set while corrections are
  prepared, so review can happen against a stable preview.
* The retained history was folded in on the owner's instruction of 2026-09-24:
  the two earlier preparation sets and their corrections became the single set
  and the single revision per record recorded above. The digest in the ledger row
  is what keeps that set from being swapped afterwards without the decision being
  taken again.
* **Open question for a later contract version.** The v0 set description says a
  set records "the approving editor", but the schema cannot express the owner's
  approval (`review.independence` has no such value and there is no decision
  field). The ledger is the record until a v1 contract decides whether approval
  belongs in the set itself, in the ledger, or in both. Extending a vocabulary
  requires a new contract version, so this is deliberately left open here.
